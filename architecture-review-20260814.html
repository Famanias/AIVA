Problem

LLM provider factory is shallow — the interface (ILLMProvider) is nearly as complex as the 4 implementations combined. Each wrapper translates one SDK to the same 2 methods. Telemetry lives only in GeminiProvider (leakage). No streaming. Fallbacks absent. UI has 4 API-key fields but only Ollama exposes model/base-URL.

Solution

Replace 4 wrappers with one OpenAICompatibleProvider using the openai SDK. Factory reads generic llm_base_url, llm_api_key, llm_model. UI pivots to "OpenAI-Compatible Endpoint" presets (Cloud, Local Gateway/OmniRoute, Local Hardware/Ollama). Add generate_stream() to ILLMProvider and list_models() for model discovery.

Wins (locality / leverage)
  • locality: all provider SDK logic concentrates in one module
  • leverage: one interface, N call sites unchanged (agents only see ILLMProvider)
  • interface shrinks: delete 3 provider SDK deps (google-generativeai, groq, openrouter not needed)
  • tests hit one interface: mock_provider already covers the seam
  • streaming becomes a first-class capability, not an afterthought
  • OmniRoute/Ollama/OpenRouter all work without code changes

Problem

AES-256-GCM implementation is duplicated in Python and TypeScript. Both derive the key from APP_SECRET with the same insecure default. Drift risk: if one changes padding/encoding, decryption fails silently. app_settings table is the single source of truth but the crypto is not.

Solution

Extract crypto to a shared module. Options: (a) compile Rust/WebAssembly and call from both; (b) publish a tiny npm package (@aiva/crypto) that Python calls via subprocess or pyodide (overkill); (c) move all settings reads/writes to a single HTTP service (FastAPI) that both sides call. Given Rule 11 (Simplicity First), (c) or a shared pure-Python/TS port is simplest.

Wins
  • locality: encryption logic lives in one place
  • leverage: one test suite covers both runtimes
  • eliminates silent drift between Python and Node decryption

  • apps/workers/app/pipelines/stage_handlers.py (optional: pass capabilities to agents)
Problem

The consolidated provider assumes OpenAI-compatible endpoints support json_object, /v1/models, streaming, etc. Reality: Ollama /api/generate has no /models, no streaming via OpenAI SDK. Some local gateways lack json_object. Current code fails at call time with LLMProviderError — no graceful degradation.

Solution

Add a ProviderCapabilities dataclass and detect_capabilities() that probes /v1/models, tries a json_object call, checks SSE streaming. Store caps on the provider instance. generate_json selects strategy at runtime. This is the adapter pattern: one interface, multiple behaviors behind the seam.

Wins
  • locality: capability logic lives in provider, not callers
  • leverage: agents/agents unchanged, just get more reliable JSON
  • tests can inject mocked capabilities for deterministic behavior
��� Tension with Rule 11 (Simplicity First)

This adds a seam (capability detection) that may be premature. The external reviewers (GPT 5.6 Luna strongly, Sonnet 5 mildly) advocate it. But current pipeline already works with weak JSON mode — the failure mode is parse error + retry. Only add this seam if you hit a real endpoint that breaks today. Otherwise YAGNI.

Problem

Leakage across the Python/Node seam: Next.js makes raw HTTP calls to LLM endpoints (test-ollama hits /api/tags; the review proposes /api/v1/settings/models hitting /v1/models). This duplicates networking logic, splits error handling, and means Tauri (desktop) would need a third copy. The Python worker already owns the provider interface.

Solution

Add FastAPI routes in the Python worker: GET /llm/models, POST /llm/test. Next.js proxies to them. The OpenAICompatibleProvider gets list_models() and health_check() methods. Single networking stack, single error taxonomy, Tauri reuses Python worker.

Wins
  • locality: all LLM HTTP logic in one module (the provider)
  • leverage: one health_check, one list_models implementation
    • eliminates Tauri networking duplication before it exists

Problem

Four provider files exist on disk but are never instantiated by the factory. They inflate the module surface, confuse AI navigation, and violate Rule 13 (Dependencies Must Justify Their Existence). The deletion test applies: deleting them concentrates zero complexity — they're already dead.

Solution

Delete the four files. Remove their imports from factory.py (they're already not called, but imports may exist). Keep MockLLMProvider — it's the test seam for CI/golden suite (two adapters = real seam).

Wins
  • locality: provider directory shows only what's real
  • AI navigability: no phantom modules to hallucinate about
  • Rule 11/13 compliance: zero dead dependencies

Top Recommendation

Candidate 1 — Collapse LLM provider factory to OpenAI-compatible provider.

This is the only candidate that passes the deletion test with a clear "yes, concentrates": the four LLM wrappers are shallow (interface ≈ implementation), share identical semantics, and the ILLMProvider seam is already the test surface (MockLLMProvider exists). Consolidating deletes 3 SDK dependencies, removes the factory switch, adds streaming, and enables OmniRoute/Ollama/OpenRouter without code changes.

Do Candidate 5 (delete dead stubs) in the same PR — zero risk, immediate cleanup.

Defer Candidate 3 (ProviderCapabilities) until a real endpoint breaks. The current weak-JSON-mode + retry works for the pipeline's two generate_json call sites (outline, script-director). Premature capability negotiation adds a seam without load-bearing justification.

Candidate 2 (unify crypto) and Candidate 4 (move LLM networking to Python) are solid deepening moves but orthogonal to the LLM consolidation. Tackle them after Candidate 1 ships and you have a stable OpenAICompatibleProvider to build on.
